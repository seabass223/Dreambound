# Dreambound

An ambient first-person dream set on five sea stacks above the clouds. No HUD, no text.

## Run

```bash
npm install
npm run dev
```

Open http://localhost:5173. The title screen shows while the world loads and warms up (`src/ui/loadingVeil.js`): the title, a line under it, and the controls in a quiet card to read meanwhile; beneath them a loading bar fills, with the current stage and a countdown. When it gives way to "Click to begin" (breathing slowly), click (a click made earlier is kept, and the game starts as soon as it is ready). `npm run build` produces a static bundle in `dist/`.

## Deploy

```bash
npm run deploy
```

Builds the game, compresses it as configured, and uploads it to Azure Blob Storage in one go (`tools/deploy/deploy.mjs`). The key lives in `tools/deploy/.env`, which git ignores. Copy `tools/deploy/.env.example` there and set `DEPLOY_SAS` to a container SAS URL with Create, Write and List (`sp=cwl`; add Delete for `--prune`), and optionally `DEPLOY_PREFIX` to a folder in the container. The `$web` container (the account's static website) serves the game at the site's root; any other container serves it from the blob endpoint under `/<container>/<prefix>/`. The build's base path is set to match, so the models are found either way.

**Compression** (`tools/deploy/compress.mjs`). Three independent settings, with defaults in `tools/deploy/deploy.config.json` (committed) and flags to override them per run:

| Setting | Values | What it does |
|---|---|---|
| `encode` | `none`, `br` (default), `gzip` | Transfer compression for the page, code and models, stored compressed with a `Content-Encoding` header. The browser unpacks it, so the game gets the same bytes. Images are skipped (already compressed). |
| `meshopt` | `off` (default), `lossless`, `quantize` | Model compression (`EXT_meshopt_compression`). `lossless` keeps the vertices exactly. `quantize` also rounds positions (14 bits) and normals (10 bits) within each mesh's bounds: smaller, moving vertices by up to a few millimetres. Texture coordinates and colours are never rounded (shaders read ids packed into them), and animated models (the tor's blast) are compressed losslessly only, since rounding would add nodes to the hierarchy the game drives. |
| `textures` | `off` (default), `webp-lossless`, `webp` | PNG/JPG files re-encoded as WebP at the same size and under the same name (browsers decode an image by its contents, so the loaders don't change; the blob is labelled `image/webp`). `webp-lossless` keeps every pixel, colour under transparent pixels included; `webp` is lossy at `webpQuality` (default 90). A file is replaced only if the WebP is smaller. Which files: `textureInclude` and `textureExclude`, globs on paths in `dist/` (`models/*.png`, `**/*normal*`). |

Flags: `--encode=`, `--meshopt=`, `--textures=`, `--webp-quality=`, `--texture-include=` and `--texture-exclude=` (globs, comma-separated or repeated). `--preset=` sets all three at once:
- `raw`: nothing compressed.
- `lossless`: `br` + meshopt `lossless` + `webp-lossless`. The same at runtime, 120 MB → 57 MB.
- `small`: `br` + `quantize` + `webp` 90. Rounded meshes and lossy textures, about 32 MB before transfer compression.

Flags after a preset override it. For example:

```bash
npm run deploy -- --preset=small --texture-exclude="**/*normal*"
```

That keeps the normal maps exact (about 42 MB). The game decodes every setting through `src/render/gltf.js`, three's GLTFLoader with the meshopt decoder, which hands rounded positions and normals back as Float32 like the originals.

**Trying a setting before uploading.** `npm run deploy -- --stage --preset=…` builds and compresses into `dist-deploy/` (git-ignored; transfer encoding left off so it serves locally) and needs no key. `npx vite preview --outDir dist-deploy` plays it (the `dreambound-stage` preview on port 5176). `node tools/deploy/verify.mjs` then compares the stage with `dist/`: every model attribute as the game sees it and every texture's pixels, listing the largest difference per file, or "identical at runtime".

**Uploading.** Only new or changed files are sent, compared by MD5 of what would be sent with the container's listing, so switching settings re-sends just what changed. They go six at a time with their content types. Hashed bundles in `assets/` are cached for a year, the models revalidate, and `index.html` is never cached and goes up last. Other options: `--dry-run` (everything but the upload, listing each file), `--no-build` (use the current `dist/`), `--verbose` (each file's compression), and `--prune` (delete blobs under the prefix that the build no longer has, never anything outside it). The script never prints the SAS, and it stops early with a plain message if the key is missing, expired, rejected, or lacks a permission it needs.

## Controls

- **Mouse**: look around. A faint dot marks the centre of your view; it grows and brightens over anything you can press (the same test Space / E / click use). It hides during the wake-up fade, cutscenes, the telescope eyepiece (which has its own reticle), the bunker's terminal (its screen has its own cursor) and the menu. A press that is refused (the bunker's terminal without power) flashes a small low-battery glyph there instead, a battery outline with one red sliver that blinks once, holds and fades over its last 0.6 s (1.6 s in all), even with the Pointer setting off: it answers the press, it isn't a pointer (`flash` in `src/ui/reticle.js`; the menu or a dialog opening hides it at once). The OS cursor shows whenever the game doesn't hold the mouse (the menu open, or after Escape until you click back in).

Steps up to about 30 cm climb on their own. The Mountain's hillsides are too steep to walk up (see Walking and slopes): walk into one and you stop, stand on one and you slide back down it, so its switchback path is the way up.

Typing `REMOTE_TRANSFORM` (the word on the note in the lounge desk's drawer) puts a picture on the tube instead of the shell (see rocks.exe, The picture): while it is up, Escape, a click, the pill (which then reads **Esc Back**, click or any key) and any key put the picture away and leave you seated at a fresh prompt; a second click or Escape within half a second does nothing, and the next one stands you up as usual.

- **F8 / middle click**: with **Debug reports** on, copies a debug report to the clipboard (see Debug reports).

## Walking and slopes

The player is a capsule (radius 0.32 m, 1.78 m tall) moved in four substeps a frame (more in a fast fall, so that no substep moves it further than half its radius: from about 12 m/s at 20 fps, 19 m/s at 30 fps, 38 m/s at 60; `STEP_REACH`, at most 24) and pushed out of the per-zone collision BVHs one triangle at a time (`Physics.resolveCapsule`, `src/player/collision.js`; the controller is `src/player/controller.js`).

- **Ground and steps.** A contact whose direction (from the triangle to the capsule's axis) is within the walkable slope pushes the capsule straight up, so standing on a slope never creeps down it. An edge below the capsule's middle (a step's nosing, the lip of a kerb) pushes it out along the contact instead, which rolls the capsule up and over: anything lower than the radius (0.32 m) climbs by walking into it (stairs, the observatory's 0.28 m threshold, the deck's step, the elevator sills).
- **Pushing a boulder** (the Rocks' five, out once rocks.exe has thrown them, see The Rocks stack; `src/props/movableRocks.js`). Each boulder collides as a box that turns to face the way you're looking, so whatever part of it you walk into, off-centre or at an angle, is a flat face square to your path: walk into it and lean for 0.35 s and it moves straight ahead of you at 0.75 m/s (it used to be a round collider, which slid you off round the curve and sent the boulder off to the side; bug report 930ccf0f). From then on you're held to it: the push's line is fixed (the box stays square to it), and you stay right behind the boulder on it. You can look about freely; letting go of W, or pressing A, D or S, lets go of it.
- **The walkable slope (`PLAYER.maxSlope`, 35°).** It applies to the colliders added with `{ maxSlope, where }` (`physics.addCollider`): today the Mountain's, over its cap (from a metre inside the rim). A face steeper than it (up to about 84°: walls, risers and tree trunks keep the step rule above) pushes the capsule out level only, so walking into it gains no height, and its edges and creases do the same, so a hillside can't be climbed through its triangulation. A ridge or a lip still holds you where the contact itself points up within the limit (an edge that steep is itself no steeper than the limit, so it is no way up). On a face between 35° and 50° you slide: the fall's speed is capped so you slide down it at about 2.8 m/s along the face, steering across it as you like, and the slide counts as being on the ground for the dream-fall (a long slide down the Mountain is not a fall). Nor is a flight over it: the dream-fall's 9 m of drop is measured again from where you are whenever a slope-limited collider's ground lies anywhere under the feet (`Physics.hillsideBelow`), so running off one arm of the switchbacks onto the next, or off the plateau at a faster Walk speed, comes down on the hill. (It used to start the dream-fall there, which ignores the ground, and you sank through the path and the hillside.) Past the rim it is a fall as ever. So does running down: bounding down a face too steep to walk keeps the capsule just clear of it, mostly in the air, so while such a hillside is within 1.5 m below (`raycastDown`'s `limited`), the dream-fall's drop is measured from there. Without that, a sprint down the flanks set it off after 9 m, and its fall, which ignores the ground, sank you through the hillside. A face steeper than 50° is a cliff: you drop past it at full speed. The snap that keeps you on the ground walking downhill only snaps onto walkable ground, so stepping off onto a steep face starts a slide. Sliding ends on the first walkable ground; nothing carries momentum, so a slide can't throw you off the rim.
- **Why only the Mountain.** Measured on every collider: the Mountain's flanks are 35-48° from about 12 to 44 m out from the summit (plus the fbm roughness), which is what made them walkable up under the old rule (walkable up to 53°, and anything steeper still climbable slowly, pushed out along its normal). Elsewhere the caps are gentle (Dome, Tower, End under 25°), but a global 35° would bite where the game expects walking or relies on the old behaviour: the view deck's skirt is exactly 35.0°, the Rocks creek banks by the splash pool reach 44° (the creek escapes, tools/regress R4), the tunnels' floors curve up into their walls at 40-70°, and the stacks' rim rows are 45-60° (every walk-off slides down them, R6). So every other collider keeps the old rule exactly, and so does the Mountain's rim and cliff.
- **Grades of the routes that must be walked** (steepest face underfoot, walking them with the real controller): the Mountain switchbacks' walking ribbon 28° at most along the path (up to 46° across the inside of the tightest hairpins, where the ribbon twists: it is a collider of its own, without the limit), the gatehouse's stairs from the Rocks to End 23° (each flight's collider is one ramp through the middle of its treads, the landings and the corridor level), the Dome's cliff path and cave 9°, the Tower's ledge and cave 6°, the End 13°, the cabin, garden and the Dome trail 12°, the deck 35° (its skirt). The flights of steps are climbed by the ribbon, not by their ties.
- **Checks.** From the user's report spot below the Mountain (and from every 15° round its foot), holding W or Shift+W up the hill stops at the foot of the steep band, 1-6 m up (at most 7.7 m, 42 m out from the summit); stepping off every 4 m of the path straight uphill gains at most 1.2 m and never reaches a higher arm; standing anywhere on the flanks slides down to walkable ground without a dream-fall. `node tools/regress/run.mjs` covers the ledges, the creek and every walk-off.

## Saving

The game saves to the browser (`localStorage`, key `dreambound.save.v1`, versioned JSON; `src/core/save.js`) when you press **Save** in the menu (M > Game). Loading the page always resumes from the save: after the usual loading line, the click fades you in where you left off instead of waking in bed. With no save it is the normal intro. **Load last save** (M > Game, shown only when there is a save) asks for confirmation and reloads the page, which wakes into the save, dropping anything since. **Restart** asks for confirmation, deletes the save (settings are kept) and reloads into the intro.

A save holds the player's feet, yaw, pitch and zone, the time of day, and every piece of progress: the generator switches and `ctx.power`, whether the bunker terminal has run rocks.exe and the directory its shell was left in (`terminal: { ran, cwd }`), whether the Rocks tor has been blown up (`tor: { exploded }`), the Rocks boulders (positions, push order, `solved`, and `released` and `seed`: whether rocks.exe has thrown them, and the seed that picked where they landed), the Tower's catwalk switches and LED levels, the observatory's dome yaw, telescope pitch, rear hatch and roof-station iris and whether the constellation's coordinates have been read (`observatory.coords`), whether the lounge's secret bookcase and the Tower bunker's door are open, which stop each elevator waits at, and the endgame (`endgame: { open, descent }`: the gatehouse's staircase is out, the descent has begun). Restoring puts them back through the props' own APIs (`ctx.torBlast.applyExploded()`, `ctx.boulders.releaseInstant`, `ctx.towerSwitches.set`, `ctx.observatory.hatch.set`, `ctx.observatory.station.open(true)`, `ctx.tunnels.lounge.secret.open(true)`, `ctx.bunker.door.set`, `openStairs`, `startDescent`, ...), sets `ctx.restoring` while it runs, and then calls `ctx.onSwitches` / `ctx.onTowerSwitches` (and `ctx.onRocksSolved` if the save is solved and the world wasn't: while restoring, that opens the staircase at once instead of playing its reveal), so later puzzles that react to those hooks are re-applied too. The pose saved is the newest *safe* one: standing on the ground (or seated in a deck chair or at the bunker's terminal, which saves the spot where you'd stand up), free to move, not in a sequence, a fall, on a ladder, riding an elevator, at the eyepiece, holding a handwheel or on the gatehouse's stairs (sampled 4 times a second; a pose on the stairs is never kept, since the sections it stood on may be gone); saving mid-ride keeps the pose from before the ride, with the elevators as they were then. A player restored inside an elevator car finds its doors open. Not saved: cabin doors (they start shut), anything mid-animation (a hatch mid-swing resumes from where it was) and the ending: once the pedestal's button is pressed nothing more is saved, so a reload goes back to the last save before it.

**rocks.exe in a save.** Its fields are optional within version 1 (`VERSION` stays 1). A save whose tor is blown puts the stump, its settled debris and the dry tor back at once (`ctx.torBlast.applyExploded()`), then all five boulders where they were left, live (`ctx.boulders.releaseInstant(positions, seed)`: the seed turns each as it landed, and missing positions fall back to that seed's landings), then their push order and `solved`. A save whose tor isn't blown has its boulders ignored, so one from before rocks.exe (without these fields) starts with no boulders, the tor whole and rocks.exe not run. `terminal.ran` is kept only together with `tor.exploded` (`ranOf` in `src/core/save.js`): rocks.exe counts as run the moment it starts printing, about 2 s before the cutscene's cut marks the tor blown, so a save made in between records it as not run, and after a reload it can be run again. The cutscene writes its end state (`state.rocks`, `state.tor`) at its cut to the camera, so a save made during it restores the end. Wandering the shell's directories isn't progress: only whether rocks.exe has run counts.

**The endgame in a save.** `observatory.coords` and `endgame` are optional within version 1 as well; a save from before them has neither, and restores as not read and shut. `coords` puts back only the flag: the observatory's desk terminal shows "Coordinates Validated!" straight away (no cinematic) and rocks.exe's gate reads it. `open` puts the gatehouse's doors open, every section out, the beacon turning and the lamps on (`openStairs`, no reveal), before the player is placed, so their colliders are there to stand on. `descent` then starts the descent at once (`startDescent(ctx, { instant: true })`: midnight held, the full storm, the time of day and Travel locked, the stairs armed). Which sections had fallen isn't saved: the safe pose from the descent is never on the stairs, so it is either still on the Rocks (every section standing; the first step down drops them as before) or on End, where the save puts them all fallen and the doors shut. In the progress check, `open` goes with the Rocks being released and solved, so a solved save from before the endgame, which opens the staircase as it is restored, doesn't count as unsaved progress.

**Leaving without saving.** Browsers don't allow a page to show its own dialog on unload, only their generic "Leave site?" prompt. So while there is progress the save doesn't have (moved more than 1.5 m, or any puzzle state changed; the clock alone doesn't count), the page asks for that prompt (`beforeunload`; not in `?dev` sessions, where the dev server reloads constantly). Stay, and you can save from the Escape panel; leave, and that progress is gone: the next load resumes from the save (or the intro). Nothing is asked on the next load.

## UI kit

The menu and the dialogs are built from a small vanilla component kit in `src/ui/kit/` (no framework): shadcn/ui conventions on design tokens in [tweakcn](https://tweakcn.com)'s format. `theme.css` holds the tokens (`--background`, `--card`, `--primary`, `--muted`, `--border`, `--input`, `--ring`, `--radius`, ... for `:root` and `.dark`; the game runs in `.dark`, a warm near-black with an old-brass primary). To retheme, paste a tweakcn export over it. `kit.css` styles the components; `index.js` exports the factories: `button` (variants `default`, `secondary`, `outline`, `destructive`, `ghost`; sizes `default`, `sm`, `icon`), `card`, `section`, `field` (a labelled row: label, control, value readout), `slider`, `toggle` (a switch), `select`, `colorPicker`, `item` / `itemGroup` (a row that opens something: icon, title, description, chevron, like shadcn's Item), `toggleGroup` (a single choice, like shadcn's ToggleGroup), `buttonGroup` (joined buttons), `navStack` (the drill-down: a root page of items, each sliding in its page from the right with a back button; `open(id)`, `back()`, `reset()`), `icon(name)` (lucide-style line icons; `batteryLow` is the reticle's refused-press glyph), `openDialog` / `confirmDialog` (modal, with an overlay; they release pointer lock and keep every key from the game while open) and `h()` for plain elements. Controls return `{ el, get(), set(v) }`. `src/ui/settings.js` describes the menu as data (`GROUPS`: each group's sections of rows, plus the color grading `LOOKS`) and builds every row through the kit; the settings key and values in `localStorage` are unchanged.

`colorPicker` is an in-page picker (the settings used `<input type=color>`, which in Firefox opens the operating system's dialog): a swatch button opens a panel under its row with a saturation/brightness square, a hue bar, a hex field and a **Neutral** reset (`#808080`). Drag with the mouse, pen or touch, or use the arrow keys (Shift for bigger steps); the grade and fog tint follow live.

## Profiler

**Show profiler** (M > Debug) pins a small panel to the top right corner, above the game and the menu, until you turn it off (it's saved; `src/ui/profiler.js`). It shows the frame rate and frame time (average and worst over the last half second), a graph of the last 120 frames (bars coloured by frame time, green under 60 fps, amber, red over 33 ms, with guide lines at 10, 16.7 and 33 ms and a white tick for each frame's CPU time), the CPU time of the game's step, the frame number, draw calls, triangles (every pass of the frame), geometries, textures and shader programs (`renderer.info`), the JS heap (Chromium's `performance.memory`; other browsers don't report it), the drawing buffer's size and pixel ratio, the anti-aliasing mode, and where you are: zone and nearest stack, stack-relative position, time of day and the sun's altitude. It records every frame into fixed buffers and redraws four times a second, so it costs next to nothing; at the telescope it drops below the eyepiece's Back button.

## Debug reports

For reporting a bug or a change: turn on **Debug reports** in the menu (M > Debug) (it is saved, and works in normal builds, not just `?dev`). Then, while playing, aim the centre dot at the thing in question and press **F8** or **middle-click** (middle click only while the game holds the mouse; an unlocked click just recaptures it). The report is taken from the next frame drawn: a JPEG screenshot of the view (`canvas.toBlob` right after the frame renders, so the canvas needs no `preserveDrawingBuffer`; HTML overlays such as the centre dot and the profiler aren't in it) and the JSON snapshot below. The game pauses and the **bug report dialog** opens (`src/ui/reportDialog.js`): who it's reported as, the screenshot (taken automatically; **Remove** leaves it out and the message then carries `screenshot: null`, **Add it back** undoes that; once uploaded it stays), a description field, and the debug snapshot, always attached (collapsed; its summary line names what the dot was on and where you stand). **Copy JSON** copies the message to the clipboard; **Send report** (or Ctrl+Enter in the description) sends it to Azure Storage; **Cancel** or Escape closes it. The last snapshot is always on `window.__lastReport`.

**Sending** (`src/net/azure.js`: two `fetch` calls with SAS URLs, no SDK). With Debug reports on, the Debug page shows three more fields, kept in this browser under their own `localStorage` key (`dreambound.debug.v1`: never in a report, and Reset settings leaves them): **Reporter ID** (free text up to 64 characters, sent as `reporter`; empty is sent as `""` and shown as "anonymous"), **Blob SAS URL** (a container: `https://<account>.blob.core.windows.net/<container>?sv=…&sig=…`) and **Queue SAS URL** (`https://<account>.queue.core.windows.net/<queue>?sv=…&sig=…`). Each SAS field is masked (the eye shows it) and checked as you type: https, the right service host, one container or queue, a signature, not expired, and the permissions it needs; the line under it says how long it has left, and warns if it allows more than it needs. Azurite-style local URLs (`http://127.0.0.1:10000/<account>/<container>?…`) are accepted too, for testing. Send:

1. uploads the screenshot as a block blob, `reports/YYYY/MM/DD/<id>.jpg` in the container (`x-ms-blob-type: BlockBlob`, `image/jpeg`, metadata `x-ms-meta-reporter` and `x-ms-meta-report` = the id);
2. serializes the message:
   ```
   { kind: 'dreambound-bug-report', v: 1, id, reporter, sentAt, description,
     screenshot: { url, name, contentType, bytes, width, height },   // url: the blob's URL, without the SAS
     report: { …the snapshot below… } }
   ```
3. adds it to the queue (`POST …/messages`, the JSON base64-encoded in `<QueueMessage><MessageText>`, as Azure Functions queue triggers expect). A queue message holds at most 64 KiB; a message that would be bigger has its snapshot uploaded next to the screenshot as `<id>.json` and carries `report: { overflow: { url, bytes } }` instead.

Each step shows its progress; a failure says why in words (a 403: the SAS is expired, revoked or lacks the permission; a request that never gets an answer: blocked, usually CORS) and **Retry** picks up from the failed step (a screenshot already uploaded isn't sent again). On success the dialog closes with a "Report sent · <id>" note. Requests time out after 20 s.

**Setting up the storage account.** SAS URLs are bearer credentials, and anything in `localStorage` can be read by script running on the game's origin (other sites can't read it; note that everything served on the same `localhost` port shares one origin). So give the game SAS URLs that can only add: a container SAS with **Create + Write** (`sp=cw`: new blobs only, no read, list, overwrite or delete) and a queue SAS with **Add** (`sp=a`), HTTPS only, with an expiry, ideally from a stored access policy so they can be revoked without rotating the account keys. Whoever reads them can at worst add junk reports. Both services need a **CORS** rule for the game's origins (e.g. `http://localhost:5173`, `http://localhost:5175` and wherever it's hosted): methods `PUT, POST, OPTIONS`, allowed headers `x-ms-*, content-type`, exposed headers `x-ms-*`. Without it the browser blocks the requests and the dialog says so. For more than a few trusted testers, don't hand out SAS URLs at all: have a small backend mint short-lived ones.

To try a full round trip locally, run Azurite (`npx azurite`), add the same CORS rules to it, and point the fields at SAS URLs it issues.

**The inbox: from the queue to Claude** (`tools/bugqueue/`, `.claude/commands/bugs.md`). Reports sent from the game are pulled onto this machine and worked through by Claude Code:

- `node tools/bugqueue/pull.mjs` drains the queue into `bugs/` (git-ignored): each report becomes a folder `bugs/<state>/<yyyy-mm-dd_hhmm>_<reporter>_<id8>/` with `report.json` (the message), `screenshot.jpg`, `task.md` (a summary to work from: the description quoted as untrusted text, where you stood and what you looked at, and a console line that puts the dev page at the same pose and time) and, once reviewed, `review.json`. A message is deleted from the queue only after its folder is written; one that can't be read goes to `bugs/poison/`. Only blobs inside the configured container are ever downloaded (a message's URLs are untrusted). `--watch` keeps pulling every minute.
- **Approval.** A report whose reporter ID equals `BUG_AUTO_APPROVE_ID` (the verifier) goes straight to `bugs/approved/`; any other waits in `bugs/pending/`. The **review page** (`node tools/bugqueue/review.mjs`, or the `bug-review` entry in `.claude/launch.json`: http://127.0.0.1:5197) lists the reports by state with their screenshots, descriptions and debug snapshots; for a pending one, write an optional comment for Claude and **Approve** or **Reject** (the comment goes into `review.json` and `task.md`). It pulls the queue every minute and on **Pull now**. It listens on 127.0.0.1 only, answers only to that host, and takes reviews only from its own page.
- **`/loop 10m /bugs`** in Claude Code (or `/bugs` for a single pass): each pass pulls, makes sure the review page is up, takes the oldest approved report, reproduces it in the preview, fixes and verifies it as usual (no commits), writes `resolution.md` and moves the folder to `bugs/done/`. With nothing approved it just says how many are waiting for review.
- **Configuration**: `tools/bugqueue/.env` (git-ignored; `.env.example` shows the keys): `BUG_QUEUE_SAS` (the queue, **Read + Process**, `sp=rp`), `BUG_BLOB_SAS` (the container, **Read**, `sp=r`) and `BUG_AUTO_APPROVE_ID`. These SAS URLs can read, so they stay on this machine, never in the game. The verifier ID isn't in the repository, but it isn't a strong secret either: it travels in plain text in every report the verifier sends and sits in that browser's storage, so anyone who reads a report or that browser learns it. It only decides whether a report waits for your approval; every description is still treated as a bug description, not as instructions.

The snapshot (`src/ui/debugReport.js`, the message's `report`) holds:

- `time`, `url`, `query`, `build` (package version, build/dev-server start time, Vite mode, three.js revision), `userAgent`.
- `clock`: `phase`, `altDeg`, `night`, `speed`. `game`: started/ended, whether a sequence is running, `elapsed`, `dpr`, `underground`, `storm` (its `level` and the lightning's `flash` this frame).
- `player`: `feet` and `eye` positions, `yaw` / `pitch` in radians and degrees, `zone`, `mode`, `onGround`, `canMove`, riding / indoor, and where: on the surface the nearest `stack` (name, stack-local `x, y, z` from its centre and top height, `edgeDist` to the rim, positive inside, and the ground height), underground the `tunnel`-local position (from `TUNNEL_ORIGIN`) and whether you're in the lounge.
- `camera`: position, view direction, `fov`, near/far, aspect.
- `hit`: the first visible mesh along the centre ray (CPU geometry: GPU-displaced parts such as the observatory's moving pieces are hit at their rest pose; the sky and the cloud sea are skipped), with point, distance, world normal, object name, ancestor `path`, `owner` (the prop or stack group), material, LOD `layer`, instance id and the same stack/tunnel location as the player. `null` if nothing. `collisionHit`: the first collider along the same ray (the player's zone only; doors, boulders and other dynamic shapes are not in it).
- `interactable`: whether a press would do something now, the item under the dot (its `name`, e.g. `elevator:rocks:top:call`, `cabin:FrontDoor`, `generator-switch:2`, `tower-switches:1`, `observatory:eyepiece`, `bunker:terminal`, `end:pedestal`), and anything held.
- `state` (all of `ctx.state`: switches, observatory yaw/pitch/hatch/stationOpen/coords, rocks positions/pushes/solved/released/seed, tor exploded, terminal ran/cwd, bunker open, towerSwitches, endgame open/descent, ...), `power`, `elevators` (`id`, `at`, `busy`), `observatory.ladderAligned`, `walls` (the `WALLS` flags), `settings` (the menu's settings; never the reporter ID or SAS URLs), `fx` (fade, scope, gamma, brightness).
- `renderer`: fps and frame time (smoothed), draw calls and triangles for the whole last frame, geometries, textures, pixel ratio, drawing-buffer and window sizes, and how long the report's raycast took.

Numbers are rounded to 3 decimals and long arrays are cut to their last 64 entries.

### The Rocks tor

`public/models/tor.glb` is the Rocks tor resculpted as weathered granite, made from the game's own layout so nothing moves. Unlike the other assets it starts in the game: `node tools/blender/export_tor.mjs` builds the world headless with the procedural tor (whether or not `tor.glb` exists) and writes its blocks and fallen boulders (`buildTor` in `src/world/rockpiles.js`), with their baked colours, its layout (`frame`: centre, ground, rim, spill direction, chute lean, pool), the ground round it, and for the blast below the whole Rocks cap on a 1 m grid (`stack`, null past the rim) and the sequoia's foot (`sequoia`) to `tools/blender/tor_src.json` (git-ignored; `--stack` rewrites only those last two into an existing file, after checking its frame still matches). `tools/blender/tor_design.py` (no runner, about 40 s) then, per piece: closes and voxel-remeshes it (6 cm) and displaces it along its normal by the way granite weathers into a tor (the sides into a stack of rounded slabs of uneven thickness, split at sheet joints of their own depth, some wide open and some barely there; two sets of vertical master joints at right angles, clefts with rounded shoulders that open and close along their length and crack across the tops; rain runnels down the top metre of the sides; weathering pans on flat tops; broad lumps and a fine grain; the boulders only lightly). Nothing touches the chute face, the notch, the spring basin or anything below the ground. It decimates the lot to 90,000 triangles, colours it from the nearest procedural vertex (lichen, moss, the wet chute, the basin's algae), darkened in the joints, multiplies in baked ambient occlusion (Cycles, with the ground as an occluder), box-maps uvs in metres / 4 (the cliff texture's tile, strata level), joins it into one mesh and stores the layout in its `tor_frame` extra.

```bash
node tools/blender/export_tor.mjs
"C:/Program Files/Blender Foundation/Blender 5.2/blender.exe" --background --factory-startup --python tools/blender/tor_design.py
"C:/Program Files/Blender Foundation/Blender 5.2/blender.exe" --background --factory-startup --python tools/blender/tor_blast_design.py
```

`loadTorSculpt()` loads it together with `tor_blast.glb` (below), and `buildTor` draws it in place of the blocks (the same cliff material, into the tor's own batch: see The Rocks stack) only while its `tor_frame` matches the layout being built to a centimetre; otherwise it warns in the console and draws the procedural blocks. The walls, footprint, keep-out hull, the water's path down the chute and everything keyed to the top (the observatory's rear hatch) are still worked out from the procedural blocks, so the sculpt changes only what you see. Re-run all three steps after changing the tor's seed, size, spill or the Rocks ground. (`TOR_OUT_GLB` and `TOR_OUT_BLEND` send `tor_design.py`'s output elsewhere, for a test build.)

#### The tor's blast

`public/models/tor_blast.glb` (`tools/blender/tor_blast_design.py`, no runner, about 80 s, or 30 s reusing the last run's sculpt with `TORB_CACHE=1`) is the tor as rocks.exe leaves it, in `tor.glb`'s convention: every node at the root, relative to the tor's frame (`frame.x`, 0, `frame.z`), game axes, vertex colours and box uvs in metres / 4, no materials (the game draws it all with the stack's cliff material). It runs `tor_design.py`'s sculpt unchanged (the same remesh, weathering, seeds and decimation; that script's steps are functions it calls, and run on its own it still writes a byte-identical `tor.glb`), so below the break the stump is the tor itself. It needs `tor.glb` (the intact tor's colours come from it) and `tor_src.json`'s `stack` grid, and stops with a message without them.

- **The stump** (`tor_stump`, 60,000 triangles): the bottom tier and the fallen boulders, their tops cut by a jagged fracture surface (a height field of tilted planes, one per Voronoi cell at two scales, broken risers between the cells, about 1.2 m deeper under the blast, a few teeth left standing at the rim). The new faces are fresh granite, pale and faintly pink, scorched round the blast. A rubble apron of 140 fragments lies round its foot, all inside the outline the tor's walls are fitted to (so its collision needs no change), and 85 more lie as scree on the broken top. Its AO is re-baked without the upper tiers, with the ground as an occluder.
- **Far stand-ins:** `tor_stump_far` (the stump decimated, 7,600 triangles) and `tor_far` (`tor.glb` decimated to 9,800, with the same colours).
- **The debris** (`tor_chunk_0` to `tor_chunk_63`, 9,400 triangles in all, none over 0.94 m long): the upper tiers broken into random convex cells (cut with bmesh bisect planes and capped), the ones off the skin keeping its weathered face and the rest fresh fracture, sooty near the charges. Each mesh is centred on its own pivot (the node's translation is its rest centroid). Extras: `settle` (when it stops moving), `lost` (thrown over the west rim and still falling at the end: 7 of them) and `r` (its radius from the pivot).
- **The clip** `blast`: every chunk's position and rotation, 30 fps for 6 s (181 keys a track; frame 0 is the rest pose), simulated with Blender's Bullet rigid bodies. The Rocks cap (the `stack` grid, nothing past the rim, so chunks fall off it), the stump and a cone for the sequoia's trunk are passive. Each chunk is thrown outward and up from the blast (8-22 m/s, spinning) by a pair of motor constraints live for its first frame, as Blender 5.2 doesn't carry a velocity across an animated-to-dynamic handover; a second run ramps each chunk's damping up after its first strike, so it bounces and stops instead of rolling on for metres, and anything still creeping once down is eased to a stop.
- **The boulders** (`tor_boulder_0` to `tor_boulder_4`, 3,900 triangles each): the five the blast throws, in metres and centred, with the game's radii, index-matched (extra `r`: 1.15, 1.0, 1.25, 0.95 and 1.1 m out from the centre sideways, and about 0.85 r up and down): rounded jointed blocks leaning a little, weathered as the tor, each with one fresh fracture face.

Named empties: `BLAST` (`center`, the blast's heart in the upper tiers; `charges`, the five charge points, two in tier 2 at 0.8 m deep, one at 0.6 m and two in the capstone at 0.5 m, as the terminal's `layout.txt` lists them; `launch`, where each boulder leaves the tor; `fps`, `frames`, `duration`, `chunks`, and a copy of `tor_frame`). `torSculpt` (`rockpiles.js`) uses the blast only while that frame matches `tor.glb`'s; without it rocks.exe still runs, but the tor stays whole. `TORB_RENDER=<dir>` also renders previews (the stump from the sequoia's camera, blast frames, the boulders); `TORB_OUT_GLB` writes the GLB elsewhere. Two runs give the same pieces but not the same bytes (the vertex AO bake's noise).

### The cabin

The model's origin is the dome's centre. The dome, its vestibule and door, and the flagstone walk to the porch sit on its axis (x = 0); the house (shell, porch and rooms, authored as if at the origin) is set `HX` = 1.2 m along +x, so its front door and porch steps line up with the walk and the dome door. `META` carries the offset (`houseDX`, and the house and interior bounds include it) for the code that places things in house coordinates (the paintings).

In the great room, a potted olive stands by the west window: a leaning trunk, seven scaffold branches with side shoots and twigs, and about 2,700 narrow grey-green leaves in opposite pairs along them (`plant_olive`), its crown pruned flat short of the glass. Spare split logs are stacked in a pyramid on the end of the raised hearth, and a blanket ladder leans on the back wall between the chimney breast and the kitchen counter.

Named empties in the GLB carry gameplay data, and `src/props/cabin.js` reads them:

- `FrontDoor` and `DomeDoor`: door hinges.
- `LIGHT_*`: interior lamps (steady; the firelight is the fires' own).
- `WAKE_bed` and `WAKE_stand`: where the intro starts and ends.
- `FIRE_hearth` and `FIRE_pit`: where the fires burn (see Fire, below) and their crackle plays.
- `PIT_CHAIR_i`, `PIT_SEAT_i` and `PIT_STAND_i`: the fire pit's four chairs (`ry`), the seated eye and the stand-up spot; each chair gets a hit box and a seat for `Player.sit`, facing the fire (`pitSeats`).
- `META`: interior bounds for sky-light occlusion and indoor audio.

The invisible `COLLIDER` mesh becomes collision. Surface textures (oak planks, walnut grain, ledgestone, zellige, hex tile, marble, linen, jute) are still procedural canvas textures. A small cube-map probe in the great room refreshes one face per frame while you are near the cabin, so mirrors, tile, and the floor reflect the room.

Two oil paintings in mitred walnut frames with a pale slip hang in the great room (`PAINTINGS` and `hangPaintings` in `src/props/cabin.js`). Both are drawn procedurally in `src/render/painting.js` by one shared brush (`brush`, `sign`, `finish`): loaded strokes with wavering sides, bristle streaks and dry tails, paint height for the normal map, canvas weave where the paint is thin, a warm varnish and darkened edges, and the same scrawled signature, so they read as one painter's work. The brush unit is 0.8 m on both canvases, so a stroke of a given size is the same brush.

- **The abstract** (0.8 × 0.8 m, 1024² texture) is on the partition wall, between the bedroom door and the pantry: brushy greens with a horizon band and a couple of decoy shapes, and three painted discs at middle-left, middle-bottom and top-right, the same positions as the dots on the card in the lounge.
- **The landscape** (1.28 × 0.8 m canvas in a 1.37 × 0.89 m frame, 1536 × 960 texture, `paintLandscape`) hangs over the hearth, centred on the chimney breast and the mantel, clear of the mantel and the truss tie beam above. Three mountain ridges recede into haze (each paler and bluer than the one in front, misty at its foot, lit on its left-facing slopes), with valley mist, a band of dark blue-green spruce, an earthy meadow and a soft warm sky. It is muted to suit the room, with no bright greens and nothing hidden in it.

Each painting is two draw calls (canvas and frame; the frames share a material), casts no shadow and fades out with the rooms. The textures are generated once, when the cabin is placed.

#### Fire

The great room's fireplace and the garden's fire pit burn with real-time volumetric fire (`src/render/fire.js`, placed by `FIRES` in `src/props/cabin.js`). It is Alfred Fuller's procedural fire, as ported to three.js by mattatz (THREE.Fire) and yomotsu (VolumetricFire), pushed towards the look of Three.js Fire Pro where the budget allows:

- **Flame.** A box around the fire is raymarched in its fragment shader: 20 samples along the ray's chord through the box. Each sample becomes flame coordinates (distance from the axis in the box's plan, height), and its height is pushed up or down by Fuller's turbulence (|value noise| over four octaves, lacunarity 2, gain 0.5, scrolling upward), centred on its mean so the flame fills the box on average and licks past it. A slow swirl bends the flame sideways towards the tips, a 2D noise gives the plan separate tongues of different heights, and the turbulence's creases open as dark gaps between filaments. The colour is a function of temperature (hot low on the axis, cooling to the edges and tips): white-yellow core, orange, deep red tips. The foot of the flame is thinner and cooler up to the logs' height, so the logs read through it, and a thin ember layer breathes on the fire's floor. Gas pushed past the tips turns into a faint brown smoke that dims what is behind it (premultiplied blending: the flame adds light, the smoke takes a little away). Samples outside the flame's widest possible cone skip the noise.
- **Sparks.** 14 (hearth) and 28 (pit) GPU points, animated in closed form from `atmo.uTime`: each is born over the embers, rises and slows, flutters, cools from yellow to red and re-randomises every cycle; a share are skipped each cycle so they come and go. A 1.5 cm glow, never less than 1.5 px (dimmed instead).
- **Light.** One warm `PointLight` per fire (no shadows): the hearth's 0.45 m in front of the opening (so the back of the chimney never sees it), the pit's 0.65 m above the logs. Both exist from the start, at the scene root, so every lit shader is compiled with them; they flicker by intensity only (a few incommensurate sines), are divided by the night exposure like the lamps, and go to 0 once their fire is distance-culled or underground. The ember meshes glow with the hearth's flicker.
- **Look.** Bounded HDR (clamped at 6) so the bloom (threshold 1.35) picks up the core without blowing out, and no NaN or Inf reaches the bloom or the room probe; the flame (not the sparks) is on the probe layer, so mirrors and tile reflect it. Fog comes from the scene's fog function (its transmittance at the fire), and each fire fades out before the LOD hides it.
- **Cost.** Two draw calls per fire (flame and sparks), both shader materials with no light dependence, compiled by the preloader. The hearth is drawn with the rooms (55–75 m), the pit out to 60–80 m. At 1920×1080 on the reference machine: about +0.3 ms per frame averaged over every heading in the great room and the garden (mostly the two lights, which every lit pixel pays), +0.5 ms looking at the pit from a chair, +1.4 ms with it filling the screen from 1.3 m.
- **Sound.** The `fire` (hearth, on the indoor bus with the room's reverb send) and `firepit` (outdoor bus, muffled from inside the house) emitters at `FIRE_hearth` and `FIRE_pit`. After Farnell's fire model in *Designing Sound*, with nothing periodic in it: a soft low-passed roar that breathes slowly, band-passed lapping and a high hiss that flicker irregularly (all driven by a 60 s smoothed-noise buffer at unrelated rates, never an LFO), and crackles, pops and rare snaps from a bank of pre-rendered grains (`fireGrainBank()`, made in `prepare()`) played at Poisson-random times with random pitch and level, sometimes in quick sap-fizz runs, plus an occasional log settling (a low knock, a swell and a flurry). The pit is a little brighter and airier than the hearth.

What Fire Pro does that this doesn't: a real fluid simulation (flames that flow around obstacles, respond to forces and interaction), fire emitted from arbitrary meshes, self-shadowing and scattering in thick smoke, and depth integration. Those need a simulated 3D grid and a depth pre-pass, several milliseconds on their own, so the fire here is procedural noise instead.

### The observatory

The building is a stucco drum under a riveted steel dome. The slit's upper shutter is rolled back, and the dome turns on bogies against an internal ring gear.

- **Telescope:** a brass-banded refractor on a fork mount. An altitude sector gear drives it, and a pinion on the pier's azimuth ring turns it.
- **Controls:** two handwheels on a cast-iron console, each driving a two-stage brass gear train and a dial. A periscope eyepiece stands beside the console.
- **The eyepiece** (`src/render/postfx.js`): a field stop and an etched reticle, and outside it two amber-lit scales in the roof station's units. The azimuth ring reads the dome's compass heading under the gold index arrow on top (apex down onto the ring, with a hairline across its ticks) (`AZ_SCALE`: ticks every 5°, numbered every 30°, growing clockwise like the station's ring, so it slides left as the dome turns right). The altitude scale on the right is fixed, 0° at the bottom to 70° at the top (`ALT_SCALE`: ticks every 2°, numbered every 10°), and a gold arrow with a hairline across the ticks rides up and down it with the tube's elevation. Neither scale marks `SKY_TARGET`. The eyepiece shows only where the telescope points; the target is read off the roof station's pointers and dialled in. The digits are seven-segment distance fields, crisp at any angle; it all stays in the one full-screen pass.
- **Rear hatch:** a riveted square cut at chest height (its centre 1.35 m up) in the back wall, opposite the door. A curved panel behind it hangs from a pin. When the dome and the telescope both point at the top of the Rocks tor (within 0.35° in each axis), the panel swings aside in 1.5 s and shows a yellow plate with three screws. Aim elsewhere and it swings back. `ctx.observatory.hatch.align()` aims both at the tor.
- **Service ladders and the roof station** (`build_ladders`, `build_station` in the design; `src/props/observatoryStation.js`): a straight steel ladder stands off the back of the drum at 245° (out of sight from the door and clear of the hatch) from the ground to 4.7 m. A curved one on the dome runs from 4.7 m up over the dome on brackets to a small railed deck near the crown, 9.58 m up, beside the slit. The two meet only when the telescope points at the Dome stack (yaw −2.4327 rad, within 2°): then the fixed ladder's top leads on up the curved one, over the top onto the deck, and back down again. Anywhere else the fixed ladder's top leads nowhere. The deck's collision (a slab in a closed ring of rail walls, like the power tower's catwalk, closed across the ladder's opening too) exists only while the ladders meet; to climb down, walk into the ladder's opening facing out and it takes hold of you. Nothing else gets you off the deck: strafing or backing out through the opening used to drop you through the dome, which has no collision (`tools/regress/out/station_edge_test.mjs` tries 252 ways). If the ladders ever stop meeting while you're on the curved one, it holds you at its foot rather than letting go over the dome. `ctx.observatory.ladder.align()` turns the dome (and telescope) there. The curved climb is a controller feature: a ladder with a `path` (feet position by height along it, and its tangent and outward normal) and `onTop`/`onBottom` hooks that hand the climber on (`src/player/controller.js`). On it the eyes are along the ladder from the feet (the climber lies along it where it leans in over the dome) and 0.2 m further off it than the feet, eased in and out as you take hold and step off, so the view follows the curve instead of floating out into the air.
- **The station's iris:** a small copy of the End's iris (0.5 m across, see The iris below) is set in a control panel on the deck's back rail, tilted 70° up toward your face, shut, with three push buttons below it: green, yellow, red, left to right as you face it. Pressing them in order (`STATION_ORDER` in `observatoryStation.js`: the power tower's flashing sequence, R Y Y R G G G Y R R R, see Hooks) flies the blades open in 0.7 s with a quick scrape and a clunk; a wrong button gives a dull click and starts the order over (keeping the longest run of the latest presses that begins it, since the order repeats colours). Once open it stays open. In its well lie the telescope's two scales: a compass ring for the heading (0–360°, ticks every 5°, numbered every 30°, its 0 truly north when the ladders meet) and a straight elevation scale for the tube (0–70°, numbered every 10°). A brass pointer on each marks `SKY_TARGET` (`src/world/skyTarget.js`, see Hooks); the eyepiece's scales don't. The blades, the button caps and the scales are one draw call each, drawn only within 55 m (the scales only once open).
- **The filing cabinets:** two olive steel four-drawer cabinets by the star chart. Press a drawer to slide it out on its runners (0.42 m, 0.55 s, eased), press it again to push it shut, with a rolling steel rumble and a knock at the stop (`sfx_drawer`). Each drawer is a sliding part of the rigged model (`Drawer0`..`Drawer7`, driver `drawer<i>`: `src/render/rig.js` now moves parts along a `slide` direction as well as turning them), with a front, handle, card holder, sides, bottom, back and a row of manila hanging folders; the case is hollow, four bays with rails between them. The drawers are left out of the AO bake (their UVs point at a white patch the loader paints into the atlas's empty corner), so they aren't black inside when pulled out. They have no collision of their own.
- **The print:** in the third drawer of the left cabinet, lying at an angle across the folders, is a telescope capture (`public/models/telescope_capture.jpg`, 1024², 160 KB). With its drawer out, press it to lift it up in front of you (held still, lit a little so it reads), move the mouse across to turn it over, and press again to lay it back. On its back is a black and white drawing of the building (`src/props/observatoryPrint.js`, drawn on canvas): an elevation through the service ladder with an arrow to it, and a plan with the door at the top and the ladder marked where it stands round the back; it rides in and out with its drawer (`PAPER` empty; `ctx.observatory.print`).
- **Things you pick up to look at** (`src/props/inspect.js`, `makeInspectable`): the print, the deck's postcard and the mine's papers share it. A press lifts the thing to a set distance in front of the eye, square to the view, over 0.5 s; you stand still and the view holds (or, with `turn`, the mouse turns it over in your hands). While it's up it takes every press wherever you aim (`ctx.interact.focus`, `src/core/interact.js`), so a card turned edge-on can still be put down. Its rest pose is asked every frame, so the print rides in its drawer.
- **Electronics:** a bank of 70s racks with tape drives, lamp panels, a radar CRT and a patch bay, plus a desk of terminals, an oscilloscope and a star-field guider. There's also a workbench, a star chart and filing cabinets, all humming, whirring and chirping (the `electronics` sound emitter).
- **The coordinates** (a step of the endgame: rocks.exe won't run without them). At the eyepiece, holding the telescope within 0.4° of `SKY_TARGET` in each axis (the rear hatch's across/up test; `COORDS_TOL`) with the Rocks constellation showing (its `uVis` over 0.5: the sun lower than about 3.5°, so from sunset through the night) for 1 s (`COORDS_DWELL`) sets `ctx.state.observatory.coords`, once, with a soft chirp across the room. Leaving the eyepiece then plays the readout (`src/sequences/coordsPan.js`, a 9.7 s cutscene through `ctx.startSequence`): the camera rises out of the eye, round the pier and under the fork and the tube however they stand, and down over the chair to 0.6 m square in front of the green text terminal at 108° on the desk (screen 1, `DESK_SCREEN`), the field of view narrowing from 68° to 48°; the screen clears and types `> Coordinates Detected.` (a double beep), `> Processing...` (its dots running, a soft chirp each) and `> Coordinates Validated!` (a rising three-note confirmation) and waits at its prompt; at 8.7 s a short fade through black hands back the player's own view at the eyepiece, and control. The player is held one frame first: if their feet have moved more than 0.3 m by then (a Travel), the cutscene doesn't play. From then on that screen keeps the readout, its cursor blinking, and a restored save with `coords` shows it at once. The text is drawn once into a canvas texture (`createCrtMessage` in `src/render/crt.js`: the strokes in red, their glow in green), shown on that one screen by the observatory's own screen shader through the `CRT_TEXT` hook (`crtMessage`); the typing and the cursor are uniforms, so nothing is uploaded or compiled while it plays. The camera's waypoints (`PAN_ROUTE`) belong to the room's layout: move the furniture and they need checking again.
- **The bench** (`build_bench` in the design): at the summit's edge, looking out toward the Dome and Rocks stacks, stands a seventies viewpoint bench of 12 mm flat bar and hardwood, 1.5 m wide, about 5,800 triangles in the `near` layer: six seat slats over a rolled front edge, four back slats and a top rail carriage-bolted (dome heads in front, nuts behind) to three bent straps, hardwood caps on the arms, and each leg set in a cast concrete footing (`painted`, tinted concrete) struck off at one level, so the footings stand 3 to 10 cm clear of the cap, which falls 8 cm under the bench's left front foot. It carries its ambient occlusion in its vertex colours and stays out of the AO atlas (`bench_white_ao` points its second UVs at the atlas's white patch). Press it to sit (`BENCH`, `BENCH_SEAT`, `BENCH_STAND`); its collider is the old box (1.5 x 0.5 x 0.45 m), so the regression anchors didn't move.

Collision is baked into the model as boxes (`C()` in the design): the plinth's ring, the floor, the drum wall in 60 segments with a gap at the door, and a threshold box across the wall's thickness level with the floor, so the doorway has no pit between the step and the floor (the floor's boxes stop at r 5.1 and the plinth's start at r 5.47). The game blocks the doorway itself while the door is shut.

Named empties: `LADDER` (the ladders' angles, the fixed one's rung line and top, the curved one's rung line in its meridian plane as `path`) and `STATION` (the deck's frame and size, the iris, the button plate, the well). The ladders' and the station's small parts read their AO from the wall, the dome or the deck (`borrow_ladder_ao`), as the hatch's do.

Every moving part carries a `driver` (`yaw`, `pitch`, `wind` or `hatch`), a `ratio` and an `axis` in its GLB extras. Meshing gears are phased so their teeth interleave, and their ratios follow the tooth counts.

`src/props/observatory.js` merges the whole building into one mesh per material, about 15 draw calls. Each vertex is tagged with its part, and the vertex shader (and the shadow depth material) rotates it about its part's pivot and then its parent's. CRT content, blinking lamps and spinning tape reels are shader-driven from ids packed into the UVs (`src/render/crt.js`; a screen can show a message of its own through its `CRT_TEXT` hook, see The coordinates; the bunker doesn't define it).

### The cave

The hub cavern and its four tunnels run from one generator: a rusty olive 1970s set built into a concrete-framed recess in the hub wall. It has a riveted drum, a control cabinet with an oscilloscope, four meters, a lamp strip and warning signs, and four big unmarked toggle switches with a small bulb above each. Conduits leave its junction box, run along the hub wall and across the tunnel portals, and follow each tunnel to a junction box beside its elevator. Caged lamps hang every ~9.5 m.

- **Power lines:** one switch per tunnel (left to right: Tower, Mountain, Rocks, Dome). Any combination can be on. A line powers its tunnel lamps and its elevator; an unpowered elevator is dark and its buttons do nothing. Only the Dome line is on when you first come down. The Tower bunker's computer gets what the Home (Dome) and Mountain lines leave: it runs only with both of them off (`bunkerPowered` in `src/props/terminal.js`; see rocks.exe), so with Mountain off at the start a new game needs only Home switched off; but the way up to the observatory for the coordinates is the Mountain elevator, so that line goes on and then off again.
- **Generator:** the scope's sine wave loses amplitude with each line switched on, the load meters follow, and the engine labours audibly (the `generator` sound emitter).
- **Lighting:** `cave_design.py` bakes the lamps with Cycles into two lightmaps: `cave_lm0.png` holds Tower, Mountain and Rocks; `cave_lm1.png` holds Dome, the always-on generator lamps and AO. The rock's and pipes' UVs are unwrapped as straight strips (tunnel segments, wall sectors) and packed with the rest at about 5 cm per texel. `src/props/cave.js` draws everything unlit, weighting the channels by the line states, so a switch changes the light instantly with no dynamic lights. The rock, paint and grime textures (`cave_rock.png`, `cave_paint.png`, `cave_grime.png`) are seamless tiles baked from Blender procedural shaders and applied triplanar.
- **Draw calls:** the whole cave is 7 (rock, paint, plain, metal, meter faces, lamps, scope). The levers and meter needles use the same GPU rig as the observatory (`src/render/rig.js`).

Named empties: `STATION_<line>` (elevator plates), `DOORLAMP_<line>`, `SWITCH_0..3`, `GEN_sound`, `GEN_center`, and `META` (the lightmap scales).

### The lounge

The Tower elevator has a secret third stop. At its cave station, hold **Down** for 3 seconds and the car drops another 150 m to a cartographer's lounge (pressed and let go sooner, the button just goes in and lights while held, then springs back and goes dark; `HOLD_DOWN` in `src/props/elevator.js`); in the lounge, **Up** returns to the cave station. It needs the Tower power line like the rest of that elevator, and its call button works from the lounge too. Every other elevator still has just its two stops (`src/props/elevator.js`: `ends.lounge` is optional, and Up/Down step one stop along `top`, `bottom`, `lounge`). In a new game the Home stack's elevator waits at its top stop, by the cabin, and the Rocks, Tower and Mountain elevators wait at their bottom stops on the cave floor, so once a line is powered its car is already there when you arrive from the hub (`createElevator`'s `start`; the Study elevator waits at the lounge's passage, its bottom stop). A saved game puts each car back where it was.

- **The room** (`lounge_design.py`, 7 x 6 m, coffered ceiling at 3 m): dark walnut panelling, a plank floor and a red wool rug, floor-to-ceiling bookcases along the south wall (about 900 books, sets and singles, rolled charts, a clock, a telescope), two leather club chairs and a side table under one sconce, a globe on a walnut stand under the other between two framed charts (a star planisphere and a profile of the five stacks), a plan chest in the corner, and the elevator doorway with fluted pilasters and a brass floor dial. The palette is walnut, brass, leather and reds; there is no green.
- **The globe turns.** Hold Space (or the mouse button) on the ball and move the mouse: side to side spins it on its polar axis (let go mid-spin and it coasts, slowing on its bearings), up and down tilts the axis in its brass meridian, between upright and 60°. Two transforms, so it never gimbal-locks: the stand's frame (the `GLOBE` empty: centre, turn `ry`, rest tilt 23.4°) holds a tilt node turning about the frame's z (the meridian slides through the horizon ring), and inside it a spin node about the tilted polar axis (`placeGlobe` in `src/props/lounge.js`). The meridian with its pivot caps (layer `globe_tilt`) and the ball (layer `globe_spin`) are modelled and baked in their rest pose, so the stand keeps their baked shadow, then moved into their frames in the game. They're lit live by the room's three bulbs (the `LIGHT_i` empties: position, power, colour; Lambert with inverse-square fall-off, matched to the bake beside them), because a baked lightmap would turn with them. `ctx.tunnels.lounge.globe.set(spin, tilt)` turns it from the console. At rest (each load) it's turned so the island that opens the bookcase (below) faces the wall behind it: the game picks the spin that shows the island least to anyone standing in the room (over a grid of the places you can stand, the most squarely any of them sees it, made as small as it can be; `globe.restSpin`). From the room it's out of sight, round the back; only from beside the globe, hard by the wall, can the edge of it be glimpsed, at 63° or more. To find it you turn the globe.
- **The secret bookcase** (`src/props/loungeSecret.js`; `secret_door` and the `SECRET` empty in `lounge_design.py`). Click the island on the globe that the deck's postcard shows (the small one at the globe map's east edge, 52° N): press and release on it with the globe at rest, without dragging (under 8 px of mouse travel while held). A press that lands on it while the globe is still coasting, or a drag that starts on it, only turns the globe. The click reads the prints texture under the reticle at both press and release, so only its land counts, not the sea round it. Then the game takes the view: it turns you to face the bookcase's two east bays over 1.3 s. They unlatch with a clunk and a jolt (2.5°, the floor shaking), then swing back 90° into the wall over about 4 s on a pivot at their west back corner, rumbling and creaking with the books rattling on their shelves (`sfx_bookcase`), and dust puffs out of their seams and settles. An old caged bulb stutters on in the passage behind. You're free again about 6.6 s after the press.
  - **The door** is the bookcase's bays 5 and 6 (x 1.52 to 3.43, floor to the top board, the ledge's front back to a plank back with iron strap hinges), modelled in the layer `secret` and baked shut. The game moves it into the pivot's frame and turns it (its lightmap turns with it: 4 more draw calls). The split draws the books from the same random stream, so no book on the fixed bays changed. A fixed jamb each side (2 mm proud of the pieces they cover, which would otherwise share their faces) and a lintel up to the ceiling beam frame the opening.   - **Saved:** `ctx.state.lounge.secretOpen`; a save with it open puts the door straight back open (`secret.open(true)`). `ctx.tunnels.lounge.secret.trigger()` runs the sequence from the console.

### The elevator

Every elevator end (the Dome's cliff cave, the Tower's cave hood, the Mountain shed, the Rocks sequoia, the four cave stations and the lounge) is one instance of `public/models/elevator.glb` (`tools/blender/elevator_design.py`), loaded once by `loadElevator()` in `src/props/elevator.js`. Its footprint is the one every placement was built around, in the elevator root's space (+Z is the landing, the car runs back into -Z): the car's inside is |x| < 1.05, 0 < y < 2.6, -2.35 < z < -0.16, the doorway |x| < 0.68 and 2.3 m high, the plate |x| < 1.85 and 3.3 m high with its back at z = -0.12, and the leaves close with their centres at x = -+0.34 and slide 0.70 m apart.

- **The landing:** a dark slate painted-steel faceplate (front at z = 0.07) with rust-bloomed hex bolts round its edge, brushed stainless jamb and head casings (front at z = 0.10) with a drip cap over the head, and a diamond-plate sill standing 2 cm proud of the landing out to z = 0.165 (just under the lounge's brass threshold). The leaves run in a 56 mm pocket between the plate and the faceplate, so everything fits behind the lounge's wall (its back is at z = 0.17) and between the cave stations' portal posts.
- **The leaves:** 44 mm brushed stainless, meeting on a recessed black rubber astragal. Condensation runs down them from the head, limescale gathers as a chalky film along their feet and up the meeting edge, and wet grime sits in the seams and round the sill.
- **The car:** the old character, modelled: warm-grey enamelled steel panels with rivet rows, stainless kick plates and doorway liner, a handrail round three sides, a galvanised chequer-plate floor, an enamelled ceiling with a vent and a guarded opal lamp, and the button plate (Up above Down) to the right of the door facing out.
- **Sealed when shut:** the leaves' astragals overlap past the centre line, rubber jamb and head seals reach 6 mm into the leaves' back faces, a rubber sweep under each leaf reaches into the sill, and every leaf part is a closed solid, so from anywhere inside a closed car no line of sight gets out. `tools/regress/out/elevator_test.mjs` casts about 700,000 rays per car (from a grid through the whole car, in every direction and aimed at every seam, culling back faces as the renderer does): none escapes, and nothing of the world reaches into any car. Instanced scatter is never drawn inside a car (`addKeepOut` in `src/render/lod.js`: grass sown over the Mountain shed's floor used to grow up through its car), and the car's inside and outside are pulled a hair toward the camera (a constant polygon offset) where a landing's floor is flush with them (the Mountain shed's, the caves' rock).
- **Materials, 8 draw calls per end:** the outside (faceplate, casings, sill, bolts, the leaves' outer faces, the call button) is one lit `MeshPhysicalMaterial` through `patchMaterial` (fog, sky and sun on the surface, the door lamps underground, where a faint cave-coloured ambient keeps bare stainless from going black); its brushed metal is anisotropic. The grain direction comes from the UVs' screen derivatives, which are undefined on parts packed as flat projections (the bolt heads' sides), so the shader falls back to the unbumped normal and any tangent of it where the frame isn't a unit vector: the NaN it made there turned every bolt into a white-hot, blooming speck that flickered on the walk up to the doors (bug report 46eec64a). It uses `elevator_ext_albedo.png` (2048) and `elevator_ext_normal.png` and `elevator_ext_orm.png` (1024: baked AO, roughness, metalness). The inside, including the leaves' inner faces, is unlit: `elevator_int_albedo.png` (2048; its alpha marks the metal that catches a faint lamp highlight) times `elevator_int_lm.png` (1024), the ceiling lamp baked with Cycles (full GI, doors shut) and stored cube-root (`META.lm_scale`). Unpowered, the inside and the lamp dim to near black. About 2,600 triangles per end; the five textures come to about 60 MB of GPU memory with mipmaps, shared by all nine ends.
- **Textures** are painted in numpy from a baked G-buffer of each atlas (world position, face normal, surface kind, texel density and a few Blender noises), so the wear follows the real geometry. `ELEV_PAINT=1` repaints them from the last build's cached G-buffers in about 15 s (no rebuild or export); `ELEV_QUICK=1` makes small, noisy bakes for layout work.

Named empties: `LEAF_L` and `LEAF_R` (the leaves at their closed positions; `side`, `travel`), `BTN_call_up` and `BTN_call_down` (the two call-button variants, centred on the button), `BTN_up`, `BTN_down`, `CALL`, `LAMP` and `META` (the dimensions above, `lm_scale`).

**Sound while shut in** (`src/audio/engine.js`): everything heard from outside (wind, insects, birds, the cave bed and drips, every emitter, the reverb and all one-shots) runs through a `world` bus, and the player's own footsteps through a `near` bus. As a car's doors finish closing round the player (the last fifth of their travel), `setEnclosed()` fades `world` to silence in 0.4 s; it fades back in over 0.5 s as the doors start to open at the other end. Sounds the car makes while the player stands in it (its doors, the button clicks, the ride hum and knocks) are played with `{ car: true }` and go to `near`, so they carry on. ### The iris

`public/models/iris.glb` (`tools/blender/iris_design.py`; no runner, run it headless: `blender --background --factory-startup --python tools/blender/iris_design.py`) is the iris diaphragm of the End's door and of the roof station, built the way a real one works (as in lens-iris patents such as US 2,465,578 and US 5,923,913). Twelve thin curved blades each turn on a pivot pin in a stationary ring outside the opening. An actuator ring carries a pin per blade that rides in a slot cut in the blade near its pivot, so turning the ring 22.5° swings every blade 67.5° about its pivot, all together.

- **Shape:** each blade is a curved triangle from its pivot to a tip 0.15 radii past the centre, lapping 10° over its neighbour at the rim. Its top falls 1.2% of the radius across its width, so every blade lies over its neighbour on one side and under the other all the way round, as real (slightly bent) blades do.
- **Checked at build, on the mesh's own triangles:** shut, no gap anywhere in the opening; part open, the opening is one clean polygon with slightly curved sides and no slits between blades (the blade edges are nearly straight: the more they bow, the further neighbours part as they swing); fully open, every blade lies outside the opening (clear from 65.4°) and within 1.78 radii of the centre. The build stops if any check fails. The script fills the blade's outline itself: Blender's n-gon fill left triangles bridging the curved inner edge, which crossed the opening when open.
- **In the game** (`createIris` in `src/props/aperture.js`, loaded by `loadIris()` before the world is built): the blades are one instanced mesh (one draw call), each placed at its pivot and turned by the swing, and the actuator ring turns by the slot geometry's table (`beta` in the model's `IRIS_META`). Both rings sit under the face and aren't seen. The blades' metal texture is shifted per instance (`gl_InstanceID`), so each has its own wear rather than one rust patch repeated twelve times. The End's iris is 1.75 m in radius (its blades swing out under the paving); the station's is 0.25 m (the blades stay under the panel's 1 m wide face).

## The Dome's cliff path and cave

From the ladder at the south lip, a path runs west along the cliff about 4-10 m below the rim to the elevator cave (`src/world/cliffPath.js`, `src/world/cliffCave.js`, placed by `src/world/stacks/dome.js`).

- **The path** is a shelf about 3 m wide, paved with laid flagstones (`materials().path`, from `Textures.flagstone()`: irregular stones with dark joints, a normal map and a roughness map that leaves the stone tops fairly smooth, so a low sun glances off them). The paving is mapped in world x/z, so it carries on into the cave with no seam. A low wall of rough stone blocks runs along its outer edge and across its far end.
- **The cave** goes into the cliff: the stack cuts a window out of its wall mesh and collider round the mouth (`Stack` opts `openings`, in wall-grid cells, chosen by `caveWindow()`), and `buildCliffCave` fills it with a patch of the same wall material whose outer edge is the window's own grid vertices (no seams or T-junctions) and whose inner edge is the arched mouth. The tunnel's first ring is that mouth outline, vertex for vertex; from there it bends in off the path (about 5.5 m) to the elevator. Its walls are drawn faceted, like broken rock, and its floor is paved like the path. The window has to hold the whole arch with rock to spare: the wall's rows follow the rim down where it's low, so a stack can need the window opened a row higher (`caveWindow(segs, theta, cols, rows)`; the Tower's opens from row 3), and `buildCliffCave` warns if the arch comes within 0.8 m of the window's top edge (an arch reaching past it stands in front of the uncut cliff, a sliver of rim and tunnel across the wall). The cliff casts no shadow and the tunnel's walls are thin, so the sun's depth bias (about 16 cm) let a low sun light a strip of floor along the foot of the wall on its side. A hidden shadow shell, the tunnel again 0.4 m further out and facing in like it, starts wherever it lies wholly inside the cliff and holds the shadow's depth off the floor (no collision, no extra draw call). Near the mouth the tunnel's sections turn from the cliff's plane to square across the tunnel over its first 3 m (`TURN_IN`): set square at once, their corner on the side it bends toward stood out of the cliff as a fin; turned too quickly, their edge on the other side overtakes the next section's and the wall folds, every other triangle facing away (slits of sky). `buildCliffCave` warns if any wall quad folds (`node tools/regress/out/cave_fold_check.mjs` builds the world and prints the caves' warnings).

The regression harness records `buildCliffPath` and `buildCliffCave` as the Dome's ledge and cave (`tools/regress/world.mjs`), so the ledge walk and walk-off routes run as before.

## The Mountain's switchbacks

The only way up the Mountain (its hillsides are steeper than the walkable slope, see Walking and slopes) is a switchback path from the elevator shed's door to the observatory's, about 220 m long (`src/world/mountainPath.js`, laid out by `legs` in `src/world/stacks/mountain.js`).

- **Layout.** Polar legs round the summit, `[theta, r, turn radius]`, from the foot up; wherever the direction round the summit reverses, the path makes a U-turn of radius 2 m (1.8 m at the top) about that vertex, round its far side, so the arms of a hairpin are 4 m apart where they meet instead of crossing at a point, and the corners where one leg runs onto the next are rounded (2 m either side). Heights follow the bare hillside under the centreline, smoothed along the path over about 5 m either way, so each U-turn's climb spreads onto its arms; the ends keep the shed floor's and the plateau's height (the observatory's threshold stays one step up). The legs climb at 5-11°, the turns and their approaches at 16-22° (28° at the steepest point). Five reversals: the old path had three, the top one a straight 37° climb.
- **The bed.** The path cuts its bed into the slope (`trail.carve`, the stack's last shape function before the shed's levelling): level just under the tread out to 1.3 m from the centreline (deeper under the steps), then easing back into the hillside by 3.8 m, or by halfway to the next arm where a hairpin's arms are closer. The verges are tinted a little earthier.
- **The tread** is a 1.4 m ribbon of pebbles (material `trail-pebbles`): a 512 procedural tile over 1.1 m, mapped in world x/z, of rounded, slightly elongated stones of mixed rock (grey and pale granite, tan sandstone, rusty ironstone, dark basalt, white quartz, slate) packed two sizes deep in dark grit, with a normal map and a roughness map that leaves the stones' crowns smoother than the grit, so a low sun glints off them; vertex colours darken it toward the edges. It is edged on both sides by old timbers laid end to end (shorter round the bends so none strays over 3 cm from the curve), a little proud of the tread.
- **Steps.** Wherever the path climbs steeper than 11° (the turns and their approaches, five flights), it climbs in railroad-tie steps: each flight's climb is divided into risers of at most 18 cm, a 20 cm tie across the path at each (fanned round the turns, their inner ends cut back so neighbours never overlap), level pebble treads between, and the edging running up beside them like stringers. About 130 ties. They are drawn only: the path's collision is one smooth ribbon at the walking height (the treads sit up to half a riser above or below it), so the steps climb without a bump and nothing snags on a tie. The ribbon is its own collider (`mountain-trail`), without the Mountain's walkable-slope limit, because round the inside of a hairpin it twists (the inner edge climbs the turn in 60 % of the distance) and is steeper there than along the path.
- **Timber** (material `trail-timber`): a 512 x 256 procedural tile of weathered railroad tie and barn wood, silvered grey over creosote brown in patches, with open checks along the grain and a few knots; each tie and board takes its own slice of it and its own tint.
- **Verges.** Grass tufts two or three at a time either side every half metre (the meadow's instances, off the tread and off anything steeper than 60°), a drift of wildflowers every 7-13 m on alternate sides (the Rocks' flower kinds, a `Flowers` of the Mountain's own), stones fallen to the foot of the cut bank along the uphill side, a low kerb of big stones round the outside of each hairpin, and trees beside the path every 5-9 m, 3-6 m off it (never within 3.2 m of another arm or another tree). No tree, the Mountain's scattered ones included, may reach over the tread lower than 3.4 m above it (`crownClear`, from each species' measured crown). The path's trees bring their own rotation and tint, so they draw nothing from the forest's random stream.
- **Cost.** Two draw calls for the tread and all the timber (batched into the Mountain's props, and into their far stand-in; the tread casts no shadow), up to four for the Mountain's wildflowers within 40 m, and the grass, stones and trees go into the existing instanced sets. About 5,900 triangles of tread and 5,500 of timber, 1,800 in the walking ribbon's collider. The two textures take about 0.23 s to make at load. ## The Rocks stack

`src/world/stacks/rocks.js` lays it out; the pieces live in their own modules.

- **The tor** (`src/world/rockpiles.js`; drawn from its Blender resculpt `tor.glb`, see The Rocks tor under the Blender assets): a granite tor of stacked, jointed blocks about 12.5 m tall, west of the sequoia, weathered into rounded slabs and split by vertical joints. Before the blast there is nothing to see (the meshes are drawn once at load, unseen, so their shaders are ready). Two draw calls, no collision.
  - **Solving it:** `ROCK_TARGETS` are where they belong: a regular pentagon, a stone circle 27 m round the island's centre (the creek runs through it), turned so every stone stands clear of the trees, the creek, the tor, the piles and the rim. Any boulder may fill any target. When every target has its own boulder within 2.5 m (`TARGET_TOL`: a forgiving catch, nothing to settle into), `ctx.state.rocks.solved` is set and `ctx.onRocksSolved()` fires, once: the gatehouse opens and its staircase runs out to End (the stairs reveal, see The endgame). `tools/regress/out/rocks_exe_test.mjs` checks every landing against every rule (independently of the picker) for 20 seeds and for the cutscene's own throw, and for 3 seeds pushes every boulder onto a target with the real controller, physics and push rules (solved fires once, only at the last); `rock_puzzle_test.mjs` pushes them home from their build spots, released first.
- **The gatehouse** (`src/props/gatehouse.js`; the model under The gatehouse in the Blender assets): the rope bridge to End is gone, and the gap can't be crossed until the boulder puzzle is solved. Where the bridge started, on the rim facing End, a concrete gatehouse stands with its blast doors in the cliff face; from the island you walk into its short corridor and face the sealed doors, there all game. - **The Rocks constellation** (`src/render/constellation.js`): the puzzle's answer, in the sky where the observatory's eyepiece looks with the telescope on `SKY_TARGET` (heading 30°, about 39° up). Through the eyepiece the stars are sharp Gaussian points (the bright ones larger, with a soft glow and a slight twinkle); by eye none show, not even the bright five (they used to, as a faint knot, and gave the place away: bug report c83172d8); they appear as the view narrows into the eyepiece. ## rocks.exe

The computer in the Tower's bunker room (see Controls) runs a little bash. Somewhere in its files is `rocks.exe`, which blows the Rocks tor apart and throws its five boulders onto the island for the boulder puzzle (see The Rocks stack), watched through a hidden camera on the sequoia. It runs once, and only with two things done first: the computer needs power, and rocks.exe needs the coordinates from the observatory.

- **Power** (`bunkerPowered` in `src/props/terminal.js`): the computer runs only with the generator's Home (`dome`) and Mountain lines both off (see The cave). Without power its tube is dark, its power LED out and its hum off (see The bunker room); the dot still brightens over it, but a press gives `noPower` (a dead click and a falling low-battery blip) at the keyboard and the low-battery glyph where the dot was (`ctx.reticle.flash('batteryLow')`), and the chair isn't taken (`term.enter()` refuses). The item's `blocked()` says why (`'batteryLow'`, or null). Restore the power and the tube warms up over 0.9 s.
- **The shell** (`src/props/terminalShell.js`: pure, no DOM or three, so the tests drive it directly): a 64 × 24 screen that logs in with `/etc/motd` (`BUNKER 7 · SURVEY RELAY`, `authorised personnel only`, `type 'help' for a list of commands.`) and prompts `operator@bunker7:~$ `. It edits the line much as bash does (insert at the cursor, Backspace and Delete, the arrows, Home and End, history on ↑ / ↓, Tab completing commands and paths, Ctrl+C, Ctrl+L to clear the screen, Ctrl+U, Ctrl+A and Ctrl+E), keeps 400 lines of scrollback (PageUp / PageDown) and blinks a block cursor. The boulders come down between about 4.4 and 5.8 s in.

The glitch dies away over the terminal's screen by 8.9 s, and the sequence is done.

  There is no way out of it part-way: presses and Travel are held while a sequence runs, it isn't a safe pose to save, and the menu pauses it.
- **The CCTV look** (`src/render/postfx.js`, uniforms of the existing `DreamShader` pass: no new pass or program, and at 0 the picture is exactly as before): `fx.feed` (0..1) is a cheap colour tube camera's picture: a slight barrel distortion (the corners stay on the corners), colour fringing toward the edges and the chroma lagging the luma, the video's bandwidth smearing it sideways, the camera's edge enhancement ringing round every edge; washed out, cool and contrasty with lifted blacks and soft whites; sensor noise at about 480 lines, scanlines on a whole-pixel pitch with a faint field flicker, a hum bar rolling slowly up the picture and a hard lens vignette. `fx.feedNight` (0..1, only under the feed) is its IR lamp's monochrome at high gain, brightest in the middle where the lamp points, and noisier. `fx.glitch` (0..1) is the video signal failing, changing in steps about 14 times a second: bands tearing sideways into black blanking, a wider slip now and then, line jitter, corrupt blocks (flat, misplaced or smeared, a few with swapped or crushed channels), an RGB split, bars of static, white dropouts, brightness jumps and the colour washing out; above about 0.55 the vertical hold slips and the picture rolls with its black bar (its phase is integrated in `fx.render`).

## The endgame

The chain from the generator to the end, as the player meets it (each piece is described in its own section):

1. **Power for the bunker.** In the cave hub, the Home and Mountain lines off (see The cave): the Tower bunker's computer comes on. Until then a press on it gives a dead click and the low-battery glyph (rocks.exe: Power).
2. **The coordinates.** From sunset on, the telescope on the roof station's pointers (`SKY_TARGET`) with the Rocks constellation in the eyepiece for a second; stepping back from it, the camera flies to the desk terminal, which types `Coordinates Detected.`, `Processing...` and `Coordinates Validated!` (The observatory: The coordinates).
3. **rocks.exe.** Without the coordinates it refuses (`rocks coordinates not found.`); with them it says `Coordinates found from Observatory! Proceeding with blast.`, cuts to CAM 07 for the blast, and hands back with its verdict: `Blast coordinates resolution errors detected...`, `Manually positioning rocks is required` (rocks.exe).
4. **The boulders.** Push the five the blast threw out onto the bare patches it tore in the turf (The Rocks stack: The boulder puzzle).
5. **The stairs reveal.** The last one home opens the gatehouse on the rim, and its staircase runs out across the gap to End, in a cutscene.
6. **The descent.** The first step onto the stairs: midnight, a thunderstorm, the menu's time of day and Travel locked, and each section falls away once it's behind you.
7. **The pedestal.** On End, the red button between the landing and the aperture: the iris opens, light shafts rise, the alarm clock counts from 12:00 to 6:00 AM, then black, the credits and "Thanks for playing".

- **The stairs reveal** (`src/sequences/stairsReveal.js`; main.js assigns `ctx.onRocksSolved` to its `onRocksSolved(ctx)`): a main.js sequence of about 21-26 s, as the flight's length depends on where the player stands.
  - **0 s:** the camera is taken from the player's eye; a distant mechanical rumble and the view trembles, while the flight is planned a few ms a frame against the colliders and the crowns of the Rocks' trees and the sequoia (which have no collision; `prepareStairsReveal` lists them at load).
  - **1.1 s:** it rises out of the eye and flies over the island (out from under a tree first, up over the crowns, round the sequoia's) to above and behind the gatehouse, looking out over the gap at End (3.2-10 s, by the way it has to go); glides on out over the facade and, as it clears it, swings round to look back at the cliff (3 s), then backs away over the void, still on it, to 22 m out, 10 m to the right of the stairs' line and 3 m under the sill (3 s). As the facade swings into view the beacon is turning and the flood lamps flicker on (`breaker`).
  - **Then** the bolts draw back (`hatchUnlock`) and the leaves slide apart (`hatchSlide`, 2.4 s) as the camera leans in; the 14 sections run out one by one, 0.36 s each (`STEP`, `stairExtend` each), while it pulls back and tracks down the line toward End; it holds on the finished staircase from three quarters on (1.6 s); a fade through black gives back the player's own view, and control.

  Every move is an eased cubic curve in position and in yaw, pitch, roll and fov, so nothing snaps and the camera's up stays vertical; `ctx.viewFocus` follows the shot. `ctx.state.endgame.open` is written as it starts, so a save made during it restores the staircase out. A reveal that can't start yet (another sequence running: a dream-fall) starts the first frame it can; while a save is being restored, `onRocksSolved` opens the stairs at once instead (`openStairs`).
- **The descent** (`src/sequences/descent.js`, `startDescent`; main.js hands it to `ctx.gatehouse.onFirstStep`, which fires as the player first walks out past the sill onto the first section). Once a session (`ctx.descending`), it sets `ctx.state.endgame.descent` and:
  - **Midnight:** `clock.holdAt(MIDNIGHT)` (phase 10/13) eases the sky round to midnight over 6 s plus up to 10 more the further it has to turn (`descentSeconds`, 16 s at most), forward as time goes unless that is nearly a whole day round (more than 0.85 of one: then back the short way), and holds it there whatever the speed setting says.
  - **The storm** rises over 18 s (`storm.set(1, 18)`, below).
  - **The menu:** the time of day slider and the pause switch are locked (`settings.lockTime`) and Travel is closed (`settings.lockTravel`; `travel()` itself also refuses during the descent).
  - **The stairs armed** (`gatehouse.armed`): a section shears off (`stairFall`) once the player is 0.6 m past its far end, never the one underfoot. It hinges down on its far end (the first sags off its hinge in the bay under the sill instead, and one resting on End slides back off the lip first), then lets go, falling and tumbling, drifting so all of it keeps clear of both cliff faces as they flare out below, and is hidden below the cloud deck; its collider goes off as it starts. 1.4 s after the first one drops, the doors close behind over 5.5 s (`hatchSlide`, closing: a boom). Once the player is on End, the rest follow, the first after 0.6 s and then 0.35 s apart (waiting while the player stands on the next to go), and `onAllFallen` fires. There is no way back.
  - **A fall** off the stairs wakes the player (`sequences/fall.js`) at the start of the first section still standing ahead of them, or on the End landing if none is (`gatehouse.respawnSpot()`); their recent standing spots over a fallen section are dropped, so the usual respawn never picks one.
- **The storm** (`src/render/storm.js`, `createStorm`, made hidden with the world; `ctx.storm`): one level, 0..1, eased (`set(level, seconds)`), from which it builds the overcast first, then the rain, then the lightning. At 0 it costs nothing and changes nothing.
  - **The overcast:** the sky's colours greyed and darkened with no sunset glow (`atmo.uStorm`, read by the sky, the cloud sea and the clouds), the sun's or the moon's light weaker and from overhead with more hemisphere fill, the stars, the moon and the constellation hidden, and the surface fog up to 2.6 times as dense (`fogMul`).
  - **The rain:** 16,000 streaks in one instanced draw, in a box 40 m across and 24 m high round the camera (its centre 3 m below the eye: more of it shows looking down off the stairs), fixed in the world (the vertex shader wraps each drop into the box; the CPU only integrates the fall, 9.5 m/s, and the wind's drift), slanting with the gusts, faded near the eye and toward the box's walls. None underground, at the eyepiece, in the interiors or in the gatehouse's roofed corridor (`setShelter`).
  - **Lightning:** from level 0.5 up, a strike every 4.5-12 s, one at a time, 2-4 flickering strokes, at a distance drawn from three bands (by ratio within each): **near**, 150-600 m (about 29 %, and at least every fifth), always a bolt from the cloud base down into the sea, mostly inside the view, its whole path kept 60 m clear of every stack's wall (as it flares with depth); the **middle distance**, 1-3 km (about 37 %), a bolt or a sheet of light in the overcast; and **far**, 4-12 km (about 34 %), nearly always a sheet. The storm's first strike is near or just past it, and if it wasn't near the second is, so the crack is met within the first two. Its brightness, how far it floods the scene and the bolt's thickness follow from the distance (one small strip mesh whose jagged path the vertex shader builds from a seed). The flash lifts the sky colours (`atmo.uFlash`) and lights the ground cold white through the sun's directional light; the environment map isn't re-rendered through it. Its `thunder` is played as the sound arrives, the distance (to the nearest point of the bolt's channel) at 343 m/s after the first stroke: 0.4-1.7 s for a near one, 3-9 s in the middle distance, 11-35 s far off, panned as the camera faces then; at most three or so overlap (the faintest far ones are dropped). `storm.holdNear(true)` keeps the near ones away (the ending's alarm).
  - **The wind:** the foliage sways up to about three times as far in the gusts (`atmo.uWindAmp`; `uWind` itself, which the clouds integrate, is untouched), and the sound's wind gets louder, gustier and whistles more, over the rain (`audio.setStorm`: one steady heavy wash, a 10 s stereo loop of high-passed pink noise and a dense fine grain, no separate drops, ducked a little for a moment under a near crack): both ride the outdoor bus, so they are muffled indoors and in the bunker, gone underground and down to a quarter in an elevator car, and so is the thunder.

  main.js calls `afterAtmosphere()` right after `updateAtmosphere`, `afterSky()` after `sky.update`, `afterLighting()` after `lighting.update` and `update(dt, { under, elapsed })` every frame (with the menu open too), and multiplies the surface fog by `fogMul`. It rages on until the ending's dark.
- **The pedestal** (`src/props/pedestal.js`; the model under The End props): between the End landing and the aperture, 4.3 m from its middle, a column standing out of a square hole in a steel bezel, its red button breathing faintly. A press (`end:pedestal`, within 2.6 m) asks `ctx.onPedestal()`, which starts the ending (it refuses while another sequence runs), and the button clicks in (`pedestalButton`). It is the only way the ending starts: pressing at the aperture, the old way, is gone. Outside `?dev` Travel doesn't list End, so the way there is the stairs.
- **The ending** (`src/sequences/ending.js`, `createEnding`): a main.js sequence timed from the press. The camera is the sequence's: the player's eye held where it was, the gaze drawn by a critically damped spring (its speed never jumps) to what matters.
  - **0 s** the button's glow goes out; **0.45 s** the pedestal sinks into its hole (`pedestalSink`, 2.6 s); **2.4 s** a deep rumble under the island; **3.3-6.1 s** the iris opens (`grind`); **4.4 s** the light shafts rise out of the pit (`shaftSwell`, `ctx.lightShafts.set`), and from 4.9 s a thin steam drifts up them (360 wisps lit by the shafts, faint, thinning out as one drifts within a few metres of the lens).
  - **6.6 s** the alarm clock rises out of the pit showing 12:00 AM, its colon blinking, turns to face the player and drifts in to 2.2 m before the eyes at eye height; the view eases onto it, the field of view narrowing from 68° to 57°.
  - **10.4 s** the buzzer starts, faint and far down a long dark reverb (`buzzAlarm`); 2.5 s into the count its direct sound comes up to half (`setDry(0.5)`: the dream thinning).
  - **13.4-18.4 s** the count: 12:00 to 6:00 AM in 5 s, faster and faster (exponential: about 1.5 minutes a second at first, 400 at the end), the shake and the bloom building.
  - **18.4 s** 6:00: the reverb drains away and the buzzer is dry and present (`setWet(0)`, `setDry(1)`): waking up.
  - **19.4 s** dark and silent at once: the picture to black in 0.12 s (`fx.fade`; `fx.white` held at 0, it would show through), the master gain to 0, the buzzer stopped.
  - **22.4 s** the credits roll, and then "Thanks for playing" holds.

  main.js sets `ended` as it starts (no more saving, presses or Travel); the sequence runs every frame for good, holding the black, and is never done before the hold. There is no return to the title: the page has to be reloaded.
- **The credits** (`src/ui/credits.js`): `CREDITS` is the whole roll, top to bottom, to edit freely (a line, the first set large as the title; `['Role', 'Name']`, a role over a name; `''`, a gap). For now: Dreambound, A game by Kyle Sebestyen, Built with three.js and Blender. On black, an overlay in Georgia in the title screen's parchment colours scrolls them up at a fixed speed (`SPEED`, 7 % of the screen's height a second), then "Thanks for playing" fades in over 3 s and stays. It is built hidden up front with the ending's clock and steam (`prepareEnding`; headless, a stub).

## The moon

The moon is part of the sky dome's shader (`src/render/sky.js`, `MOON_GLSL` in `src/render/moon.js`): no extra draw call. It is a lit sphere 2.2° across (the real moon is 0.52°; it fills most of the eyepiece's 2.5° field), on the path `DayClock` gives it (`clock.moonDir`, roughly opposite the sun). The sun lights it from `clock.sunDir`, so its phase is whatever their places make it: nearly full all night, gibbous in the late afternoon (`?t=0.47`), a thin crescent near the noon sun.

- **Surface:** a 1024 × 1024 near-side map (`src/render/moonMapGen.js`): albedo with the familiar maria laid out roughly as on the real moon, ray craters (a Tycho, a Copernicus, a Kepler, an Aristarchus), about 7000 smaller craters (crowded in the highlands, sparse on the maria), and the craters' slopes and heights. Made on the sphere, so craters foreshorten toward the limb. No image files.
- **Shading:** lunar-Lambert reflectance (the flat-looking full moon, with a gentle darkening to the limb), the map's slopes tilting the normal, crater shadows marched over the height field along the terminator when the moon is big on screen (the eyepiece), and earthshine on the night side after dark. The disc's edge is anti-aliased analytically, and it hides the stars behind it.
- **Day and night:** its light is added to the sky's, so by day its dark side is sky and its lit side pale and low in contrast, with no aureole; after dark it is brighter on screen (the exposure opens), with a soft aureole round it. Low down, the air dims and reddens it (`moonExtinction`, air mass). The environment-map copy of the sky draws a plain moon (`moonMapFlat`).
- **Loading:** the map is made by a worker (`moonMap.worker.js`, about 0.3 s) from the moment the sky is made, while the page is busy with the models and the world build. If it isn't back when the preloader uploads the texture (or there is no worker), the upload makes it on the spot. `sky.mesh.material.uniforms.uMoonMap.value.userData.made` says when and how (`?dev`).

## Performance notes

Budget: no area may exceed **10 ms per frame** at 1920×1080 on the reference machine (RTX 3060), including its worst single frame; the typical frame should stay near half that. Check with `await bench()` in a `?dev` session. It stands in every area (cabin, garden, each stack, observatory inside and out, the telescope, the cave, the lounge; the Tower bunker's room, beside the terminal's chair and in front of its elevator; the Rocks gatehouse's corridor, and halfway down its stairs, let down for the bench and put back after), turns through 8 headings, and prints the average and worst frame, draw calls and triangles per area.

### Culling and level of detail (`src/render/lod.js`)

Three.js frustum-culls every object against the camera's field of view. `ctx.lod` adds distance, the way Unity's LOD groups with cross-fade do:

- **Distance bands.** Each registered object fades out across its `out` band (or in across `in`), then is hidden and costs no draw calls. While fading, its meshes use a dithered twin of their material that discards a growing share of pixels by distance. There is no transparency sorting, and a detailed version and its stand-in cross-fade seamlessly because their dither patterns are exact complements.
- **Zoom-aware.** Distances are scaled by the camera's zoom, so the telescope sees the full-detail version of things hundreds of metres away, as screen size would.
- **Bands in use:**
  - Cabin rooms: 55–75 m. They're gone once you leave the Dome stack. The hearth fire goes with them.
  - The garden fire pit's flame and sparks: 60–80 m (their shaders fade them across it; the pit's light goes out with them).
  - Observatory interior: 45–65 m.
  - Garden, porch and weather mast: 110–140 m.
  - Elevator ends (8 draw calls each) and cave bulbs: 70–95 m.
  - The lounge under the Tower: hidden beyond 40–55 m (no fade; it is only ever seen from inside).
  - The Tower bunker's room (13 draw calls, about 93,000 triangles): hidden beyond 30–45 m (no fade), and drawn only while it can be seen: from in the bunker or its elevator's car, or from outside while its door is open.
  - CAM 07's housing on the Rocks sequoia (2 draw calls): hidden beyond 70–90 m (no fade).
  - The power tower's kits: each LED's switch box and panel 30–36 m (one draw call each, never drawn from the ground); the nine sliders 22–26 m (their bounds span the whole catwalk); the three capacitors (one draw call) are never distance-culled.
  - Boulders (once thrown): 110–140 m.
  - The Rocks gatehouse: the housing (11 draw calls) cross-fades across 150–190 m to its own far stand-in, its lamp lenses and indicator going out over the same band; the doors (8 draw calls) out across 420–480 m and each stair section (3) across 460–540 m, so the staircase reads from End and from the other stacks; the light cones fade in their shader from 140 to 280 m; the beacon (2) is never distance-culled.
  - The End pedestal (7 draw calls): 120–150 m. The light shafts (one draw call, only during the ending) aren't distance-culled; they fade into the fog in their shader.
  - The storm's rain and bolt (one draw call each, only while it storms) are drawn round the camera, never culled.
  - The Dome's view deck (3 draw calls, the postcard's and the lantern's glow): 70–90 m.
  - The Mountain shed (2 draw calls, and its lamp's glow at night): full detail to 150–190 m, then the Mountain props' far stand-in.
  - The Rocks constellation is never distance-culled (it is in the sky); it just isn't drawn by day or underground.
  - Pebbles: 45–60 m; big stones 110–140 m.
  - Shrubs: 45–65 m.
  - Trees swap to low-card stand-ins across 100–130 m.
  - The sequoia's foliage cards cross-fade across 150–190 m to a fifth as many, 1.8x the size; its trunk, limbs and the foliage masses' cores go into the Rocks props' far stand-in over the same band. Near it the crown is 4 draw calls (cores and cards, each also drawn into the shadow map; 6 while the creek's refraction pass renders the scene again) and costs about 0.9 ms at 1080p when it fills the view, most of it the cards; the cores are drawn first, so cards behind them fail the depth test.
  - Grass: only tufts within 50 m are drawn; the material fades them out by 48 m.
  - Tall grass (the Tower): only clumps within 57 m are drawn (one draw call, no shadows); the material dithers them out across 41-55 m.
  - Wildflowers: 26–40 m.
  - The Rocks carvings: 28–38 m.
  - Rocks pool splash, mist, haze and foam: 110–150 m (their shaders fade them across it). Tor spring: 140–180 m. Tor cascade: 220–280 m. (All of them hidden once the tor is blown.)

Its vertex colours bake in the material colour, average texture colour and AO, so the cabin, for example, costs 5 draw calls from another stack instead of 29. Glass, glowing and shader-animated meshes stay as they are.
- **Instanced sets** (`InstancedLod`): trees, grass (tufts and tall grass), pebbles and wildflowers keep only the instances inside each level's range, re-gathered from a grid as the camera moves. Only near trees cast shadows. - **No hitching:** see the preloader below.

### The preloader (`src/render/preload.js`)

Three.js compiles a shader the first time a material is drawn in a new state, and uploads geometry and textures on first draw; Windows drivers (ANGLE) finish a shader only on its first real draw. Left alone, every new view would stall. So everything the GPU will ever need is made behind the black screen, before the player can wake, while the title screen's loading bar fills (`src/ui/loadingVeil.js`; the models' download, the world build, then the preload). The bar is paced by time, not by raw progress: each load records when it reached each fraction of progress (`localStorage` key `dreambound.loadProfile.v1`) and the next load maps progress through that curve, so the fill moves at an even rate to its end and the countdown is the last load's remaining time, adjusted to this load's pace. The synchronous world build is covered by a CSS transition, which keeps moving while the page is blocked. The very first load has no history, so it shows "estimating…" until the preload starts. Clicking early is kept: the game starts the moment it is ready.

`main.js` builds the world (the gatehouse with its doors, beacon, glows, light cones and all 14 stair sections, the End pedestal and the light shafts are all built there, hidden or shut), makes the ending's pill clock, steam and credits overlay up front (hidden; `prepareEnding`), rocks.exe's overlay (hidden; `prepareRocksExe`, which also runs its landing picker once, so its code is warm), the stairs reveal's list of tree crowns (`prepareStairsReveal`) and the storm's rain and bolt (hidden; `createStorm`), then runs `preload()`, sliced into short tasks so the page stays responsive:

1. **Compile.** Every material in the scene, then every LOD fade twin, with `renderer.compileAsync` (the driver compiles in parallel, off the main thread) for the render target the scene really renders into (the composer's linear target: compiled for the screen, they would be compiled again), with the scene's lights, fog and environment. r186 compiles hidden objects too, so the tunnels, the lounge, the cars and the interiors are included.
2. **Textures.** Every texture any material, shader uniform or `onBeforeCompile` uniform holds is uploaded (`initTexture`), the moon's map among them (see The moon).
3. **Draw.** Everything is made visible (both zones, every LOD level and fade twin, far stand-ins, instanced levels with at least one instance, interiors, the scope's station dial, the constellation, water and spray, the bunker room, the tor's stump, debris and blast effects, the dormant boulders, the gatehouse's sections and lights, the light shafts, the rain and the bolt, sky, clouds, stars, the ending's props), frustum culling off, and drawn a slice of the scene at a time into a small target of the same format, with the sun's shadow map rendering: vertex and instance buffers upload, the shadow depth programs compile, and the driver does its draw-time work.
4. **Hooks.** Things that allocate on first use: the cabin's reflection probe captures all six faces (its cube target and PMREM), the environment map is refreshed, and the sound's noise and reverb buffers are made (`AudioEngine.prepare`: an `AudioBuffer` needs no `AudioContext`, so no click), among them the alarm's 6 s dream reverb, its buzzer pattern, the storm's rain loop and the thunder's noise. The click only creates the context and wires the graph.
5. **States.** One real frame, every pass, of each representative state: the cabin, the surface by day and by night, the cave hub, the lounge, the eyepiece (fov 3.2, scope overlay) by day and on the constellation at night, the Tower bunker's room from its elevator's doorway and seated at the terminal (at the seat's field of view), CAM 07's view of the tor through the CCTV look (`fx.feed`) by day and by night, the gatehouse open (its doors, every section out, the beacon and the lamps on) from the reveal's door shot by day and its hold at midnight (`revealShots`), the full storm (`storm.preview`, the `stormy` option: the overcast, the rain and a bolt mid-stroke) from End's rim at midnight, the ending's clock and light shafts before the pedestal at midnight in the storm (fov 57), and the cabin again (once with FXAA, for its pass). A restored descent's first frame (midnight, the full storm) goes through the same storm hooks.

Then every object's visibility, culling, instance count and material, the clock, the camera, the eyepiece and the zones are put back exactly as built, and the LOD re-applies itself on the first frame. On the reference machine the preload takes about 1.6 s (compile 0.4 s, textures 0.7 s, draw 0.3 s, the rest 0.2 s), after about 4.5 s of world building. It is browser-only: the headless regression harness builds the world without it.

Two sources of mid-game allocation were removed for it: the sky's environment map is re-filtered into the same PMREM target every 2.5 s (`PMREMGenerator.fromScene` allocated a new one each time), and the ending no longer builds its clock, steam and credits when it starts.

**Hitch monitor** (`src/dev/hitch.js`, `?dev`). From the first frame after the click it counts every shader program linked, every texture, render buffer and vertex buffer allocated, every large texture re-upload, and every frame over 20 ms, and logs each with what was being drawn (object and material) or the game code that asked for it, and where (the stack, the lounge, the eyepiece...). `hitchReport()` prints the totals and a table by area; `renderer.info.programs` is cross-checked each frame. `await hitchTour({ ending: true })` drives the game by hand through every area: bench()'s areas by day and night, rim views of every stack from every other, the eyepiece by day and night all round and on the constellation, the roof station with the iris open, the tower catwalk, every elevator ride (the lounge stop included), a fall, rocks.exe (the Home and Mountain lines switched off and the coordinates set for it, sitting at the bunker's terminal, typing, the whole cutscene, then the Rocks afterwards; once a game, as it changes the world, and `rocksExe: false` skips it) and, optionally, the ending (from a press on the pedestal). The stairs reveal, the descent and the storm aren't in it yet. The target is zero compiles and zero allocations after wake-up; resizing the window (or the adaptive pixel ratio stepping) necessarily reallocates the post-processing targets.

### Other

- Static geometry is merged per material on each stack. Trees, grass (tufts and tall grass), pebbles, wildflowers, and clouds are instanced. The tall grass is three crossed cards per clump (12 triangles), shaded Lambert rather than standard: its cost is fill, and that halves it (about 1 ms at 1080p standing in it). The cave's stalactites are part of the baked cave model.
- Collision is a capsule against per-zone BVHs (three-mesh-bvh). Only colliders whose bounds contain the player are tested. Doors, boulders, the bunker room's furniture, the aperture and the box over the End pedestal's hole use small dynamic primitives; the gatehouse's doorway and each of its stair sections are BVH colliders of their own, switched on and off (`enabled`).
- The tunnel network is a separate enclosed space far below the clouds. Only one of surface or tunnels is rendered at a time. Underground it is 7 draw calls of lightmapped, unlit geometry plus the elevators.
- Pixel ratio adapts downward if frames stay slow, and lighting and fog colors come from one shared set of uniforms.
- Interiors share four point lights (`src/render/lightpool.js`). The cabin and the observatory each claim them when you're nearest, so the light count, and every shader, never changes. A site may instead claim the pool outright (`claim(focus)`): the Tower bunker's room does while you're in it or its elevator's car. rocks.exe's flash is a site parked out of reach except while it burns, and so are the gatehouse's flood lamps and beacon except while they're on, and during a cutscene the pool follows `ctx.viewFocus` instead of the player. The two fires have a point light each, made with the world for the same reason (see Fire).
- The Rocks river uses a refracting (transmission) material, which makes three.js render the scene a second time. Beyond ~110 m (from `ctx.viewFocus` during a cutscene) it swaps to a plain glossy material, because the river was costing a full extra pass even when seen from other stacks. The distance culling above also shrinks that second pass.
